## Why claims fail

[Four colluding verifiers](#four-colluding-verifiers-many-verifiers). Claim: the party cannot prove, for any citizen, that it holds every one of that citizen's credential uses of some kind (every alcohol purchase, say). It fails: measured 2.

- [Neighbouring issuance anchors](https://bakobo.github.io/keri-priv-analysis-suite/attacks/#neighbouring-issuance-anchors-kel-anchor-adjacency "Each issuance is recorded in order in the issuer's public key event log. When one citizen's copies are issued one after another, their records sit next to each other, which ties them together.") is enough on its own. Cause: the generator's stack settings issuance_order = 'per-citizen', decoys = 0. Owner: the issuer and any orchestrator: mix issuance order across citizens.
- [First-seen times in the issuer's log](https://bakobo.github.io/keri-priv-analysis-suite/attacks/#first-seen-times-in-the-issuers-log-kel-first-seen "The issuer's public log carries the time each entry was first seen, from a server clock, untouched by any coarsening of the registry times. One citizen's issuances cluster in time.") is enough on its own. Cause: the generator's stack settings first_seen = 'exact', issuance_order = 'per-citizen'. Owner: the issuer and the holder's wallet: the first-seen times a published KEL replay carries.
- [Neighbouring registry creations](https://bakobo.github.io/keri-priv-analysis-suite/attacks/#neighbouring-registry-creations-registry-inception-adjacency "Registries created in a batch and handed out in order give one citizen registries created next to each other in the issuer's public log, which ties that citizen's credentials together.") is enough on its own. Cause: the generator's stack settings registry_allocation = 'fifo', issuance_order = 'per-citizen'. Owner: the issuer: random registry allocation.
- [Timestamp clustering](https://bakobo.github.io/keri-priv-analysis-suite/attacks/#timestamp-clustering-timestamp-clustering "Every credential's registry entry carries the time it was issued, to the microsecond. One citizen's copies are issued milliseconds apart, so their times stand out as a cluster.") is enough on its own. Cause: the generator's stack settings dt_granularity = 0.0, issuance_order = 'per-citizen'. Owner: the issuer, any orchestrator and batch commitment: coarse dt.

- Verifier-side bits are a lower bound on what presentation bytes can reveal: the scorer counts declared attributes, while a selectively disclosed age-band presentation can carry a full birthDate (tick 6hat).

## Attacks the catalogue does not yet make

Silence on these channels is not a result. Each is tracked in this repository's tick ledger.

- timestamps and nonces carried by the presentation protocol itself (tick 27nu)
- calibration of join confidence when citizens hold different numbers of copies (tick 2mcg)
- truncated, re-encoded and split identifiers in logs (tick 34kz)
- discovery material inside presentations, such as OOBI paths that name a citizen's agent (tick 3f3n)
- the sensitivity of bits to the population model's declared correlations (tick 3ikg)
- holder-side custodial stores: a mailbox's message store and a hosted agent's account database (tick 5aaa)
- timing joins between an asynchronous issuer's operation log and issuance anchors (tick 5im4)
- linkage across a credential's lifecycle: renewal, re-issuance, revocation cohorts and pool top-ups (tick 5sdj)
- recovering undisclosed low-entropy attributes from a compact block's SAID when the block carries no salt (tick 63ga)
- attribute values a presentation's bytes carry beyond what it declares disclosed (tick 6hat)
- active probing that needs a live stack, such as cache-warmth or response-timing oracles (tick 7pan)

## What this report does not claim

- a global passive network adversary
- transport-level fingerprints (TLS, connection reuse)
- re-identification from behavioural quasi-identifiers alone
- what a holder chooses to disclose, beyond counting its bits
- breach detection
